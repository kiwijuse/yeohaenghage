# 백그라운드 업로드

> 앱을 꺼도 사진 10장이 올라가게 만들기

[← 목록으로](../README.md#깊이-들어간-이야기)

---

## 문제

커뮤니티에 여행 사진을 올립니다. 10장, 원본 그대로면 30MB가 넘습니다. 업로드에 1~2분이 걸립니다.

사용자는 그동안 앱을 보고 있지 않습니다. **올리기를 누르고 홈으로 나갑니다.** 지도를 보거나, 메시지를 확인하거나, 화면을 끕니다.

순진하게 만들면 이 시점에 업로드가 멈춥니다. 다시 들어와 보면 아무것도 올라가 있지 않고, 사용자는 처음부터 다시 사진을 고릅니다.

여기에 여행지의 네트워크 사정이 겹칩니다. **끊기는 게 기본값**인 환경입니다.

---

## 01 · 세 가지 실패 지점

실패할 수 있는 지점은 셋이었습니다.

| 지점 | 무슨 일이 일어나나 |
|---|---|
| 앱이 백그라운드로 감 | OS가 앱의 실행을 늦추거나 멈춤 |
| 앱이 강제 종료됨 | 메모리에 있던 작업 목록이 통째로 사라짐 |
| 네트워크가 끊김 | 전송 중이던 요청이 실패 |

세 번째는 재시도로 해결됩니다. 어려운 건 앞의 둘입니다.

---

## 02 · 업로드를 앱 생명주기 밖으로

첫 번째 해법은 업로드를 **화면과 분리하는 것**입니다.

업로드 작업을 포그라운드 태스크로 돌립니다. 알림 영역에 진행 상태가 표시되고, 사용자가 앱을 나가도 OS가 이 작업을 계속 살려 둡니다.

Flutter의 백그라운드 진입점은 **일반적인 코드 흐름에서 절대 호출되지 않습니다.** 시스템이 직접 부릅니다. 그래서 릴리스 빌드 최적화가 "이 함수는 아무도 안 부르네"라고 판단해 **통째로 지워버립니다.**

```dart
@pragma('vm:entry-point')
void uploadTaskEntryPoint() {
  // ...
}
```

이 표시가 "시스템이 부를 테니 지우지 말라"는 뜻입니다. 디버그 빌드에서는 잘 되다가 릴리스에서만 안 되는, 원인을 찾기 까다로운 종류의 문제입니다.

> [!IMPORTANT]
> 안드로이드와 iOS의 사정이 다릅니다. 안드로이드는 포그라운드 서비스로 실행을 유지할 수 있지만, **iOS는 앱이 백그라운드로 가면 배터리를 아끼려고 이벤트 루프 자체를 멈춥니다.** 네이티브가 업로드를 마치고 결과를 보내와도, 그걸 받을 Dart 쪽이 잠들어 있어 처리되지 않습니다. "서버에는 올라갔는데 앱은 성공 처리를 못 하는" 상태가 됩니다. 이 경우 결과를 받아 처리할 최소한의 실행 단위를 따로 깨우는 구조가 필요합니다.

---

## 03 · 큐를 메모리에 두지 않기

두 번째 해법은 더 단순합니다. **작업 목록 자체를 디스크에 씁니다.**

```
사용자가 올리기 누름
      │
      ▼
업로드 큐에 넣고 → 즉시 저장소에 기록
      │
      ▼
순차 처리 → 한 건 끝날 때마다 큐 갱신 후 다시 기록
```

앱이 강제 종료돼도 큐는 남아 있습니다. 다음 실행 때 `main()`에서 저장된 큐를 복원하고 남은 작업을 이어서 처리합니다.

```
main()
 ├─ 저장된 업로드 큐 복원
 ├─ 남은 작업이 있으면 처리 시작
 └─ 화면 띄우기
```

사용자 입장에서는 **앱을 다시 켰더니 알아서 마저 올라가 있습니다.**

처음에는 진행률까지 저장하려고 했는데, 결국 **작업 단위(사진 한 장)로만 기록**하는 쪽으로 갔습니다. 절반쯤 올라간 파일을 이어서 올리려면 서버 쪽 지원이 필요하고, 그 복잡도를 감당할 만큼 얻는 게 크지 않았습니다. 한 장을 처음부터 다시 올리는 비용이 훨씬 쌌습니다.

---

## 04 · 올리기 전에 줄이기

가장 효과가 큰 최적화는 **덜 보내는 것**이었습니다.

요즘 폰 카메라는 사진 한 장이 3~5MB입니다. 그런데 이 사진이 실제로 보이는 곳은 커뮤니티 피드의 카드 이미지와 상세 화면입니다. 원본 해상도가 필요한 자리가 없습니다.

### 압축률을 고정하면 둘 중 하나가 손해다

처음에는 품질을 하나로 못 박았습니다. `quality: 70` 같은 식으로요. 그런데 사진마다 결과가 크게 달랐습니다.

- 하늘이나 벽처럼 **단순한 사진**은 70으로도 200KB밖에 안 나옵니다. 더 좋게 보낼 수 있었는데 손해를 봅니다.
- 골목이나 숲처럼 **복잡한 사진**은 70으로도 2MB를 넘깁니다. 목표를 못 지킵니다.

고정 품질은 "용량을 지키는 것"과 "화질을 아끼는 것" 중 하나를 반드시 포기하게 됩니다. 필요한 건 **사진마다 다른 답**이었습니다.

### 목표 용량을 만족하는 가장 높은 품질을 찾는다

품질을 올리면 용량이 커집니다. **단조 증가**입니다. 그러면 "용량 제한을 넘지 않는 가장 높은 품질"은 이분 탐색으로 찾을 수 있습니다.

```dart
Future<File?> compressImage(File imageFile, {int max_size_kb = 650}) async {
  int low = 20;    // 이 아래로는 화질이 못 봐줄 정도가 된다
  int high = 95;   // 이 위로는 용량만 늘고 눈에 띄는 차이가 없다
  File? bestFile;

  while (low <= high) {
    final mid = (low + high) ~/ 2;

    final result = await FlutterImageCompress.compressAndGetFile(
      imageFile.path, outputPath,
      quality: mid,
      format: CompressFormat.jpeg,
      minWidth: 1280, minHeight: 1280,
      keepExif: false,          // 촬영 위치가 그대로 실려 나가지 않도록
    );
    if (result == null) { high = mid - 1; continue; }

    final sizeKb = await File(result.path).length() / 1024;

    if (sizeKb <= max_size_kb) {
      bestFile = compressedFile;   // 통과했으니 후보로 잡고
      low = mid + 1;               // 더 좋은 품질을 노려본다
    } else {
      high = mid - 1;              // 넘쳤으니 품질을 낮춘다
    }
  }
  return bestFile;
}
```

품질 구간이 20~95이므로 **최대 7번**(`log₂76 ≈ 6.2`)이면 답이 나옵니다. 선형으로 훑으면 최악 76번입니다.

| | 고정 품질 | 이분 탐색 |
|---|---|---|
| 단순한 사진 | 목표보다 한참 작게 — 화질 손해 | 목표에 가깝게 **높은 품질로** |
| 복잡한 사진 | 목표 초과 — 업로드 실패·지연 | 목표 안에서 **가능한 최대 품질** |
| 압축 횟수 | 1번 | 최대 7번 |

**압축을 7번 하는 비용**을 감수한 선택입니다. 사진 한 장에 수백 밀리초가 더 들지만, 이 작업은 이미 백그라운드 큐에서 돌고 있어서 사용자는 기다리지 않습니다. 반대로 용량을 못 맞춰 업로드가 실패하면 그건 사용자가 그대로 체감합니다. **어느 쪽 비용이 사용자에게 보이는지**로 판단했습니다.

> [!NOTE]
> `keepExif: false`가 함께 들어간 이유가 있습니다. EXIF에는 **촬영 위치와 시각**이 들어 있습니다. 여행 사진이라 집이나 숙소 좌표가 그대로 실릴 수 있어, 압축하면서 같이 털어냅니다. 용량도 조금 줄지만 목적은 그쪽이 아닙니다.

한 장이 650KB를 넘지 않으니, **3~5MB짜리 사진 열 장이 6.5MB 아래로** 들어옵니다. 30MB가 넘던 것이 5분의 1 수준이 됩니다. 업로드 시간이 그만큼 줄고, 사용자의 데이터 요금도 줄어듭니다.

압축과 함께 **가로·세로 크기를 함께 보냅니다.**

서버가 필요해서 받는 값은 아닙니다. 이 값이 쓰이는 자리는 **나중의 화면**입니다. 이미지 크기를 모르면 피드를 그릴 때 이미지가 로드된 다음에야 높이가 정해집니다. 그러면 이미지가 하나씩 로드될 때마다 아래 콘텐츠가 밀려 내려갑니다. 크기를 미리 알면 빈 자리를 정확한 비율로 잡아 두고 그 안에 이미지를 채울 수 있습니다. 레이아웃이 흔들리지 않습니다.

## 05 · 파일은 서버를 거치지 않는다

파일을 앱 서버로 보내고 서버가 다시 스토리지에 올리면, 서버가 대역폭과 메모리를 그대로 떠안습니다. 사진 10장짜리 요청이 동시에 여러 개 들어오면 서버가 먼저 무너집니다.

그래서 **프리사인드 URL** 방식을 씁니다.

```
① 앱 → 서버 : "사진 3장 올릴게요"
② 서버 → 앱 : 스토리지에 직접 올릴 수 있는 임시 URL 3개
③ 앱 → 스토리지 : 파일 직접 업로드      (서버를 거치지 않음)
④ 앱 → 서버 : "업로드 끝났어요, 게시글 저장해주세요"
```

파일 본체는 서버를 지나가지 않습니다. 서버는 권한을 발급하고 결과를 기록하는 일만 합니다.

이 구조는 **재시도에도 유리합니다.** ③에서 실패하면 그 파일만 다시 올리면 됩니다. 게시글 전체를 처음부터 다시 만들 필요가 없습니다.

---

## 06 · 채팅 이미지는 따로

같은 구조를 채팅 이미지에도 씁니다. 다만 큐를 **분리했습니다.**

이유는 우선순위입니다. 커뮤니티 게시글 업로드는 몇 분이 걸려도 괜찮지만, 채팅에서 사진을 보내는 건 대화 흐름 안에 있어서 늦으면 안 됩니다. 같은 큐에 넣으면 사진 10장짜리 게시글 뒤에 채팅 이미지 한 장이 줄을 서게 됩니다.

## 트레이드오프

| 선택 | 얻은 것 | 감수한 것 |
|---|---|---|
| 포그라운드 태스크 | 앱을 나가도 업로드 계속 | 알림이 계속 떠 있음 · 플랫폼별 동작 차이 |
| 큐를 디스크에 저장 | 강제 종료에도 복구 | 작업마다 쓰기 발생 |
| 업로드 전 압축 | 전송량과 시간 감소 | 화질 손실 · 압축 자체의 CPU 비용 |
| 프리사인드 URL | 서버 부하 없음 · 재시도 쉬움 | 요청이 2단계로 늘어남 |

---

## 아쉬운 점

**실패한 작업을 사용자에게 제대로 보여주지 못했습니다.** 재시도는 하지만, 최종적으로 실패했을 때 "무엇이 안 올라갔는지"를 알려주는 화면이 없었습니다. 사용자는 게시글이 없다는 것만 알고 이유는 모릅니다.

---

## 마치며

업로드 코드를 짜면서 **"앱이 살아 있다"를 전제하지 않는 법**을 배웠습니다.

화면 코드를 쓸 때는 사용자가 앱을 보고 있다고 가정해도 됩니다. 하지만 업로드처럼 오래 걸리는 일은 사용자가 지켜보지 않는다는 게 정상입니다. 그 전제를 바꾸는 순간 필요한 설계가 완전히 달라졌습니다.
