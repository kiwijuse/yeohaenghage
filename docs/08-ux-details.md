# UX 디테일

> 에러 로그에 안 잡히는 버그들

[← 목록으로](../README.md#문서)

---

## 문제

QA에서 이런 피드백이 옵니다.

> "메뉴를 세 번이나 열었다 닫았다 했어요."
> "누른 게 먹힌 건지 모르겠어요."
> "뒤로 가기가 잘 안 눌려요."

크래시가 아닙니다. 에러도 아닙니다. **어떤 추적 도구에도 잡히지 않습니다.** 그런데 사용자는 여기서 이탈합니다.

이 문서는 그런 종류의 문제들을 다룹니다.

---

## 01 · 클릭 수가 아니라 인지 부하

"모든 기능은 3번의 클릭 안에 있어야 한다"는 말이 있습니다. 2001년에 나온 오래된 규칙인데, 이후 여러 사용성 연구에서 **클릭 수와 이탈률 사이에 뚜렷한 상관관계가 없다**는 결과가 나왔습니다.

실제로 사용자를 붙잡아 두는 건 클릭 수가 아니라 **"지금 내가 어디 있고 다음에 뭘 눌러야 하는지 아는가"** 였습니다. 다섯 번을 눌러도 길이 명확하면 답답하지 않고, 두 번 만에 도착해도 그 두 번이 어디로 가는지 모르면 헤맵니다.

이 관점에서 정리한 원칙 네 가지입니다.

**① 숨기지 않는다.** 햄버거 메뉴 뒤에 핵심 기능을 넣지 않고 하단 탭에 꺼내 뒀습니다. 화면 다섯 개가 항상 보입니다.

**② 이름을 짧고 명확하게.** `거래 내역서 및 영수증 알림` 대신 `정산`, `알림`으로 나눴습니다. 정확한 이름보다 **짧고 예측 가능한 이름**이 낫습니다.

**③ 같은 것은 같은 자리에.** 뒤로 가기는 항상 왼쪽 위, 더보기는 항상 오른쪽 위. 화면 200개에서 이걸 지키는 게 생각보다 어려웠습니다.

**④ 엄지가 닿는 곳에.** 한 손으로 폰을 쥐면 엄지가 편하게 닿는 범위는 화면 아래쪽입니다. 자주 쓰는 조작을 위쪽 구석에 두면, 사용자는 매번 손을 고쳐 쥐어야 합니다.

## 02 · 보이는 크기와 누르는 크기는 다르다

디자이너가 준 아이콘이 24dp입니다. 그대로 구현하면 **터치 영역도 24dp**가 됩니다.

책상에 앉아 테스트하면 잘 눌립니다. 문제는 이 앱을 쓰는 상황이 **걸으면서, 캐리어를 끌면서, 흔들리는 버스 안에서**라는 것입니다. 그 상황에서 24dp는 자주 빗나갑니다.

해결은 간단합니다. **보이는 크기는 그대로 두고 누르는 영역만 넓힙니다.**

```
   보이는 것            실제 터치 영역
  ┌────────┐         ┌──────────────┐
  │  24dp  │   →     │  ┌────────┐  │
  └────────┘         │  │  24dp  │  │  48dp
                     │  └────────┘  │
                     └──────────────┘
```

투명한 여백을 둘러 터치 영역을 최소 48dp(약 9mm, 성인 손가락 끝 너비)로 만듭니다. 디자인은 하나도 바뀌지 않고 **안 보이는 반경만 커집니다.**

> [!TIP]
> 이걸 안 하면 사용자는 "안 눌렸다"고 생각하고 **같은 자리를 연타합니다.** 그러다 정말로 두 번 눌리면 이번엔 중복 요청이 나갑니다. 작은 터치 영역은 UX 문제로 시작해서 데이터 문제로 끝납니다.

## 03 · 기다림을 줄이는 게 아니라 다르게 느끼게 하기

API 응답이 1초 걸린다고 합시다. 이걸 0.5초로 줄이는 건 서버의 일입니다.

하지만 **사용자가 느끼는 대기 시간**은 프론트엔드에서 줄일 수 있습니다.

### 스켈레톤 UI

빈 화면에 스피너 하나를 돌리면 사용자는 **아무 정보도 얻지 못한 채** 기다립니다. 대신 앞으로 들어올 데이터의 모양을 회색 블록으로 미리 그려 두면, 같은 1초라도 "지금 불러오는 중이고 곧 이런 게 나오겠구나"를 알 수 있습니다.

곧 나올 화면의 **윤곽을 미리 보여주는 것**만으로 체감 시간이 줄어듭니다.

### 낙관적 UI

하트를 눌렀을 때 서버 응답을 기다린 다음에 색을 바꾸면, 누를 때마다 반 박자씩 늦습니다.

그래서 **누르는 즉시 색을 바꾸고** 요청은 뒤에서 보냅니다. 실패하면 그때 되돌리고 알립니다. 하트 같은 조작은 거의 항상 성공하므로, 성공을 기본값으로 두는 편이 훨씬 자연스럽습니다.

> 이 두 가지를 적용하면 서버가 하나도 빨라지지 않았는데도 앱이 빠르다고 느껴집니다.

## 04 · 애니메이션에는 적정 구간이 있다

화면 전환 애니메이션 시간을 여러 번 조정하면서 정리된 감각입니다.

| 길이 | 느낌 |
|---|---|
| **100ms 미만** | 번쩍이는 느낌. 뇌가 "무엇이 어디로 갔는지" 따라가지 못함 |
| **200~300ms** | 자연스러움. 대부분의 화면 전환에 적합 |
| **500ms 초과** | 앱이 무겁고 느리게 느껴짐 |

너무 빠른 것도 문제라는 게 의외였습니다. 애니메이션의 목적은 예쁘게 보이는 게 아니라 **"이 화면이 저 화면에서 왔다"는 공간 감각을 유지시키는 것**입니다. 너무 빠르면 그 정보가 전달되지 않아서, 오히려 방금 전환이 일어났다는 것만 알고 어디서 왔는지는 모르게 됩니다.

가속도 곡선은 선형보다 **처음 빠르고 끝에서 감속하는 형태**가 자연스러웠습니다. 현실의 물체가 그렇게 움직이기 때문입니다.

### 이어지는 요소

목록에서 숙소 카드를 눌러 상세로 들어갈 때, 카드의 이미지가 **그대로 상세 화면의 헤더로 이어지도록** 했습니다.

이미지가 사라졌다가 다시 나타나는 대신 연속적으로 커지면, 사용자는 "방금 그 숙소가 맞다"는 걸 의심하지 않습니다. 화면이 바뀐 게 아니라 **같은 것을 더 자세히 보는 것**처럼 느껴집니다.

## 05 · 눌렀다는 신호

버튼을 눌렀을 때 아무 반응이 없으면, 사용자는 안 눌렸다고 판단하고 다시 누릅니다.

그래서 터치에 즉각적인 시각 반응을 넣고, 중요한 조작(예약 확정, 결제)에는 가벼운 진동을 함께 줬습니다. 응답이 오기 전이라도 **"받았다"는 신호**는 즉시 줄 수 있습니다.

이건 [낙관적 UI](#낙관적-ui)와 같은 생각입니다. 서버의 답변과 사용자에 대한 반응을 분리하는 것.

## 06 · 온보딩

첫 실행 화면은 이 앱에서 가장 공들인 화면 중 하나입니다.

<div align="center">
<img src="../assets/demos/onboarding.gif" width="260" /><br>
<sub>인트로에서 로그인까지</sub>
</div>

브랜드 인트로가 먼저 뜨고, 이어서 네 장의 페이지가 서비스를 설명합니다. 각 페이지의 요소들이 **한꺼번에 나타나지 않고 순서대로** 등장합니다. 제목이 먼저, 그다음 설명, 그다음 이미지 순으로 시차를 두었습니다.

한 번에 다 보여주면 사용자는 어디를 봐야 할지 모릅니다. 시차를 두면 **시선의 순서가 정해집니다.**

여행하게는 "혼자 여행하는 사람이 동행을 만난다"는, 설명이 필요한 서비스입니다. 첫 화면에서 이 개념이 전달되지 않으면 사용자는 그냥 나갑니다. 그래서 여기에 애니메이션을 쓴 건 장식이 아니라 **설명을 순서대로 읽히게 하려는 장치**였습니다.

## 아쉬운 점

**접근성을 챙기지 못했습니다.** 스크린 리더가 읽을 수 있는 라벨을 이미지와 아이콘에 붙이지 않았습니다. 글꼴 크기도 시스템 설정을 따라가지 않습니다([디자인 시스템 문서](07-design-system.md) 참고). 위에서 "터치 영역을 넓혀 실수를 줄였다"고 썼는데, **정작 화면을 볼 수 없는 사용자는 앱을 쓸 수 없었습니다.** 디테일을 챙겼다고 말하기에는 빠진 것이 큽니다.

**실제 사용자 테스트를 거의 못 했습니다.** 여기 적은 판단들은 대부분 팀 내부의 감각과 QA 피드백에서 나왔습니다. 정식 출시까지 가지 못해서 진짜 사용자의 행동 데이터를 볼 기회가 없었고, **어느 판단이 맞았는지 확인하지 못한 채 끝났습니다.**

---

## 마치며

UX 디테일은 **하나하나가 사소해 보인다는 게 특징**입니다. 터치 영역 24dp를 48dp로, 애니메이션 400ms를 250ms로. 각각은 몇 줄짜리 수정입니다.

그런데 이런 것들이 쌓인 결과를 사용자는 "이 앱 잘 만들었다" 또는 "뭔가 불편하다"로 뭉뚱그려 기억합니다. 어느 쪽이든 구체적인 이유를 대지는 못합니다.

버그는 재현 경로가 있고 고쳤는지 확인할 수 있습니다. 이런 문제들은 그렇지 않아서, **의식적으로 찾아 나서지 않으면 영원히 발견되지 않습니다.**
