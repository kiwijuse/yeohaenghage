# 실시간 메시지

> 소켓이 죽은 걸 모르는 소켓 · 오프라인에서도 열리는 채팅방

[← 목록으로](../README.md#깊이-들어간-이야기)

---

## 문제

여행하게의 채팅은 세 종류입니다.

- **1:1** — 게스트와 호스트, 또는 사용자끼리
- **그룹** — 숙소 단위 대화방
- **동행** — 동행 신청이 수락되면 **자동으로 만들어지는** 방

마지막 것이 특히 중요했습니다. 처음 만나는 사람들이 모이는 자리라, 방이 안 열리거나 메시지가 안 가면 서비스의 핵심 약속이 깨집니다.

그런데 이 앱을 쓰는 환경이 문제였습니다. **여행지, 이동 중, 지하철, 엘리베이터.** 네트워크가 끊기는 게 예외가 아니라 기본값인 곳들입니다.

---

## 01 · 연결이 살아 있다는 착각

Socket.IO는 자동 재연결을 제공합니다. 그런데 실제로 겪은 문제는 **연결이 끊기는 것**이 아니라 **끊긴 걸 아무도 모르는 것**이었습니다.

지하철에 들어가면 이런 일이 생깁니다.

```
클라이언트: 연결됨 ✓          실제: 패킷이 아무 데도 안 감
서버:      연결됨 ✓          실제: 상대가 사라진 걸 모름
```

TCP 연결은 명시적으로 끊기지 않으면 살아 있는 것처럼 보입니다. 라이브러리의 `disconnect` 이벤트는 오지 않습니다. 사용자는 메시지를 보내고, 전송된 것처럼 보이고, 실제로는 아무 데도 가지 않았습니다.

그래서 직접 물어봅니다.

```dart
_heartbeatTimer = Timer.periodic(const Duration(seconds: 25), (_) {
  if (message_socket?.connected == true) {
    message_socket?.emit('ping');
  } else {
    _attemptReconnect();
  }
});
```

서버가 `pong`으로 답하면 연결이 진짜로 살아 있는 것입니다. 답이 없으면 **연결됨이라고 표시돼 있어도** 죽은 것으로 보고 재연결 절차를 밟습니다.

연결 옵션도 여행 환경에 맞춰 조정했습니다.

| 설정 | 값 | 이유 |
|---|---|---|
| 재연결 시도 | 사실상 무제한 | 터널을 몇 분씩 지나도 포기하면 안 됨 |
| 재연결 간격 | 1초에서 시작, 최대 10초 | 처음엔 빠르게, 계속 실패하면 배터리를 아낌 |
| 연결 타임아웃 | 30초 | 느린 네트워크에서 성급하게 포기하지 않도록 |

> [!NOTE]
> 라이브러리의 자동 재연결과 **직접 만든 재연결 사다리가 함께** 돕니다. 중복처럼 보이지만 역할이 다릅니다. 자동 재연결은 소켓이 스스로 끊겼다고 판단했을 때만 동작합니다. 하트비트는 **소켓이 끊긴 줄도 모르는 경우**를 잡습니다.

## 02 · 인증이 만료되면

소켓도 REST와 같은 토큰으로 인증합니다. 그래서 토큰이 만료되면 둘이 거의 동시에 끊깁니다.

여기서 소켓이 자기만의 갱신 로직을 갖고 있으면 [API 클라이언트 문서](04-api-client.md)의 그 문제가 그대로 재현됩니다. 그래서 소켓도 **같은 락을 씁니다.**

```
연결 실패 (인증 오류)
      │
      ▼
handleTokenRefresh()   ← REST와 공유하는 락
      │
      ▼
새 토큰으로 핸드셰이크 정보 교체 → 재연결
```

REST와 소켓이 동시에 인증 오류를 만나도 서버로 나가는 리프레시 요청은 한 번입니다.

---

## 03 · 네트워크가 없어도 채팅방은 열려야 한다

두 번째 축은 로컬 저장입니다.

메시지를 서버에서만 들고 있으면, 네트워크가 없을 때 채팅방을 열었을 때 **빈 화면**이 나옵니다. 사용자 입장에서는 대화가 사라진 것처럼 보입니다.

그래서 메시지를 로컬 DB에 함께 저장합니다.

```
chatrooms        방 정보 (이름 · 종류 · 대표 이미지)
messages         메시지 본문 · 보낸 사람 · 시각
userchatrooms    참여자 · 방별 알림 설정
following_list   팔로잉 목록
profile_url_list 방별 참여자 프로필 이미지
```

`profile_url_list`가 방별로 나뉜 이유가 있습니다. 프로필 이미지는 채팅 목록에서 가장 많이 그려지는 요소인데, 이걸 매번 네트워크에서 가져오면 방 목록을 열 때마다 이미지 수십 개를 요청합니다. 방 단위로 저장해 두면 **목록이 즉시 뜹니다.**

동작은 이렇습니다.

```
채팅방 열기
   │
   ├──▶ 로컬 DB에서 즉시 읽어 화면에 그림     (네트워크 없어도 여기까지는 됨)
   │
   └──▶ 소켓 연결 확인 → 놓친 메시지 동기화 → 화면 갱신
```

사용자는 기다리지 않습니다. 지난 대화는 바로 보이고, 새 메시지가 나중에 채워집니다.

---

## 04 · 메시지를 한 건씩 처리하지 않기

오래 끊겼다가 돌아오면 밀린 메시지가 한꺼번에 들어옵니다. 이걸 한 건씩 처리하면 두 가지가 터집니다.

- 메시지마다 DB 쓰기 → 디스크 I/O 폭증
- 메시지마다 상태 알림 → 화면이 수십 번 다시 그려짐

그래서 **묶어서 받고 묶어서 반영합니다.** 배치로 받은 메시지를 한 번에 저장하고, 알림은 마지막에 한 번만 보냅니다. [상태 관리 문서](03-state-management.md)에서 찜 상태를 한 번에 채웠던 것과 같은 원리입니다.

---

## 05 · 소켓이 화면 밖에서 화면을 옮겨야 할 때

푸시 알림을 탭하면 해당 채팅방으로 이동해야 합니다. 문제는 이 시점에 **화면 트리 밖**이라는 것입니다. 알림 핸들러에는 `BuildContext`가 없습니다.

그래서 최상위 네비게이터에 대한 키를 하나 들고 있고, 소켓과 알림 핸들러가 그 키를 통해 화면을 전환합니다. 우아하진 않지만 이 문제에서는 표준적인 방법입니다.

## 트레이드오프

| 선택 | 얻은 것 | 감수한 것 |
|---|---|---|
| 25초 하트비트 | 죽은 연결을 빨리 감지 | 주기적 네트워크 사용 · 배터리 소모 |
| 사실상 무제한 재연결 | 터널을 지나도 복구됨 | 서버가 정말 내려간 경우에도 계속 시도 |
| 메시지 로컬 저장 | 오프라인에서도 대화가 보임 | 로컬과 서버의 정합성을 맞춰야 함 |

정합성이 가장 까다로웠습니다. 같은 메시지가 소켓과 동기화 양쪽에서 들어와 중복으로 저장되거나, 순서가 뒤바뀌는 경우를 계속 다뤄야 했습니다. 메시지 ID를 기준으로 걸러내는 방식으로 처리했지만, 이 부분은 지금도 가장 손이 많이 갔던 코드로 남아 있습니다.

## 아쉬운 점

재연결 로직이 두 겹으로 겹쳐 있습니다. 라이브러리 자동 재연결과 직접 만든 사다리가 동시에 돕니다. 역할이 다르다고 위에 적었지만, 솔직히 말하면 **처음에 라이브러리 동작을 충분히 이해하지 못한 채 직접 만든 것이 남은 결과**에 가깝습니다. 지금 정리한다면 하트비트로 감지만 하고 복구는 라이브러리에 맡기는 쪽으로 단순화할 것입니다.

메시지 동기화 코드가 한 파일에 1,800줄 가까이 뭉쳐 있습니다. 소켓 이벤트 처리와 로컬 DB 접근이 섞여 있어서, 어느 쪽 문제인지 나누기 어려웠습니다.

---

## 마치며

실시간 기능에서 어려운 건 메시지를 주고받는 일이 아니었습니다. **연결이 불확실하다는 사실을 다루는 일**이 어려웠습니다.

"연결됨"이라는 상태를 믿지 않는 것, 네트워크가 없을 때도 화면이 비어 있지 않게 하는 것. 이 두 가지가 실제 사용자 경험의 대부분을 결정했습니다.
