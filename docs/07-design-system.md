# 디자인 시스템

> 시안 390×779를 모든 기기에 맞추기

[← 목록으로](../README.md#문서)

---

## 문제

디자이너는 한 가지 크기의 화면 위에서 작업합니다. 우리 시안은 **390 × 779** 였습니다.

여기서 779는 기기의 전체 세로 길이가 아니라, **상태바와 내비게이션 바를 뺀 실제로 그릴 수 있는 영역**입니다.

문제는 이 값이 기기마다 다르다는 것입니다. 시안의 400px 카드를 그대로 쓰면:

- 작은 기기에서는 화면의 3분의 2를 차지하고
- 큰 기기에서는 절반만 차지합니다

같은 화면이 기기마다 다른 비율로 보입니다. 디자이너가 의도한 여백과 균형이 무너집니다.

---

## 01 · 비율로 환산하기

시안의 px를 그대로 쓰지 않고, **현재 기기의 실사용 영역 비율로 환산해서** 씁니다.

```dart
const double design_width  = 390;
const double design_height = 779;

/// 앱 시작 시 한 번 채워 넣는다 (상태바·내비게이션 바 제외한 크기)
double available_screen_width  = 0.0;
double available_screen_height = 0.0;

double reHeight(double px) => available_screen_height * px / design_height;
double reWidth(double px)  => available_screen_width  * px / design_width;
```

사용하는 쪽은 이렇게 됩니다.

```dart
Container(
  width: reWidth(342),      // 시안에서 342px였던 카드
  height: reHeight(180),
  margin: EdgeInsets.only(top: reHeight(16)),
)
```

**개발자가 시안의 숫자를 그대로 옮겨 적을 수 있다**는 게 이 방식의 가장 큰 이점이었습니다. 디자이너가 "여기 여백 16"이라고 하면 `reHeight(16)`이라고 씁니다. 중간에 계산하거나 해석할 필요가 없습니다.

디자이너 한 명이 화면 200개를 그리고 개발자 둘이 그걸 구현하는 상황에서, **소통 비용을 0으로 만드는 것**이 실제로 큰 차이를 만들었습니다.

---

## 02 · 글자만 환산하지 않은 이유

눈여겨볼 부분은 여기입니다.

```dart
double reText(double sp) => sp;   // 환산하지 않고 그대로 반환
```

레이아웃은 비율로 늘리면서 글자 크기는 시안 값을 그대로 씁니다.

처음에는 글자도 같이 환산했습니다. 그런데 작은 기기에서 본문이 12px 아래로 내려가면서 **읽기가 먼저 힘들어졌습니다.** 레이아웃이 조금 어긋나는 것보다 글자가 안 읽히는 게 훨씬 큰 문제였습니다.

작은 기기에서는 한 줄에 들어가는 글자 수가 줄어들 뿐, 글자 자체는 읽을 수 있는 크기로 남는 편이 나았습니다.

> [!IMPORTANT]
> 이 선택에는 명백한 대가가 있습니다. **OS의 글꼴 크기 설정을 따라가지 않습니다.** 시스템 글꼴을 키워 둔 사용자에게도 앱은 같은 크기로 보입니다. 접근성 관점에서는 잘못된 선택이고, 다시 만든다면 최소 크기를 보장하면서 시스템 배율을 일정 범위 안에서 반영하는 쪽으로 갈 것입니다.

함수 이름을 남겨 둔 건 의도적이었습니다. 나중에 정책이 바뀌면 이 함수 하나만 고치면 앱 전체에 적용됩니다. 실제로는 끝까지 바꾸지 못했지만, **바꿀 수 있는 자리를 남겨 두는 것**과 아예 없는 것은 다릅니다.

## 03 · 타이포그래피

두 서체를 함께 씁니다.

| 서체 | 쓰이는 곳 | 이유 |
|---|---|---|
| **Noto Serif KR** | 브랜드 문구 · 온보딩 · 주요 제목 | 명조체의 무게감이 "기억"이라는 브랜드 정서와 맞음 |
| **Pretendard** | 본문 · 버튼 · 목록 · 입력 | 화면용으로 설계된 서체라 작은 크기에서도 안정적 |

세리프를 제목에만 쓰는 건 흔한 조합이지만, 이 서비스에서는 특히 잘 맞았습니다. 여행하게의 카피는 `출발은 혼자, 기억은 같이` 처럼 짧고 감성적인 문장이 많습니다. 이런 문장은 명조체에서 훨씬 잘 읽힙니다. 반면 예약 화면의 숫자와 조건들은 고딕이 아니면 답답합니다.

---

## 04 · 아이콘

아이콘은 전부 SVG로 관리하고, 색은 쓰는 쪽에서 지정합니다.

```
images/icon/
├─ home_*        홈 · 하단 탭 (11개)
├─ travel_*      지도 · 검색 (8개)
├─ community_*   피드 · 글쓰기 (11개)
├─ message_*     채팅 (5개)
├─ profile_*     마이페이지 (11개)
├─ schedule_*    일정 (5개)
└─ manager_*     숙소 편의시설 (22개)
```

**파일 이름 앞에 화면 이름을 붙였습니다.** 폴더를 나누는 대신 접두어를 쓴 이유는, 파일 탐색기에서 정렬만 해도 화면별로 묶이고 검색할 때 `travel_`만 쳐도 관련 아이콘이 모두 나오기 때문입니다. 아이콘이 80개를 넘어가면서 이 규칙이 실제로 도움이 됐습니다.

`manager_` 접두어가 붙은 22개는 편의시설 아이콘입니다. 에어컨 · 세탁기 · 와이파이 · 주방 같은 것들인데, 숙소마다 어떤 시설이 있는지를 **비트마스크 하나**로 주고받습니다. 시설이 20개가 넘어도 정수 하나면 충분하고, 아이콘 목록을 그릴 때 비트를 순회하면 됩니다.

### 지도 마커는 미리 그려 뒀습니다

평점이 표시된 지도 마커는 런타임에 합성하지 않고 **미리 렌더링한 이미지를 씁니다.** 0.0부터 10.0까지, 선택 상태와 비선택 상태를 각각 준비했습니다.

지도에 마커 수십 개를 한 번에 그리는데, 마커마다 배경과 숫자를 합성하면 그 비용이 전부 지도가 움직이는 순간에 몰립니다. 미리 만들어 두면 이미지를 얹기만 하면 됩니다. 에셋 용량은 늘지만 앱 크기에서 차지하는 비중이 크지 않았고, **지도가 부드럽게 움직이는 쪽이 훨씬 중요했습니다.**

---

## 05 · 화면 가장자리까지 쓰기

앱은 상태바와 내비게이션 바 뒤까지 화면을 확장해서 그립니다. 시스템 바는 투명해집니다.

여기서 실무적인 문제가 하나 생깁니다. **상태바 아이콘 색이 배경에 따라 안 보입니다.** 흰 배경 화면에서는 아이콘이 어두워야 하고, 지도나 사진처럼 어두운 배경에서는 밝아야 합니다.

화면마다 자기 배경에 맞는 시스템 바 스타일을 선언하고, 화면이 전환될 때 그 값이 적용되도록 했습니다. 사소해 보이지만 이걸 빠뜨리면 **특정 화면에서만 상단 시계가 안 보이는** 현상이 생깁니다.

---

## 아쉬운 점

여기가 이 프로젝트에서 가장 크게 남은 빚입니다.

**공통 컴포넌트를 끝내 만들지 않았습니다.** 버튼 · 앱바 · 바텀시트 · 카드를 화면마다 다시 선언했습니다. 초반에는 화면을 빨리 찍어내는 데 유리했습니다. 남의 코드에 의존하지 않으니 서로 부딪히지도 않았고요.

문제는 화면이 100개를 넘어가면서 시작됐습니다. 버튼의 모서리 반경을 바꾸자는 얘기가 나오면 수십 곳을 고쳐야 했습니다. 실제로 호스트 이벤트 등록 화면 네 개는 서로 거의 같은 코드가 각각 1,300줄씩 들어 있습니다.

**150k줄이라는 숫자는 규모의 증거가 아니라 이 부채의 크기입니다.**

**색상과 간격에는 이 체계를 적용하지 못했습니다.** 화면 비율은 함수로 정리해 뒀으면서, 정작 색은 `Color(0xFF228B22)` 같은 값을 쓰는 자리마다 직접 적었습니다. 브랜드 색이 하나 바뀌면 전체 검색으로 찾아야 합니다. 크기에 대해 옳다고 생각한 원칙을 색에는 적용하지 않은 건 일관성 없는 판단이었습니다.

**환산 기준이 두 개로 갈렸습니다.** 초기 기준(390×779)과 나중에 온보딩을 만들면서 추가한 기준(390×844)이 공존합니다. 새 기준에는 글꼴 배율을 일정 범위로 제한하는 개선이 들어갔지만, 기존 화면에 적용하려면 200개를 검증해야 해서 미뤘습니다. **개선된 방식을 만들어 놓고 옛 방식과 함께 두는 것이 가장 나쁜 결과**였습니다.

---

## 마치며

이 프로젝트의 디자인 시스템은 **절반만 성공했습니다.**

크기 환산 함수 세 개는 잘 작동했습니다. 개발자가 시안 숫자를 그대로 옮겨 적을 수 있게 만든 것만으로도 소통 비용이 크게 줄었고, 그건 사람이 셋인 팀에서 결정적이었습니다.

하지만 디자인 시스템은 값을 환산하는 것보다 **재사용 단위를 만드는 것**이 본질이었습니다. 그쪽을 미뤘고, 화면이 늘어난 뒤에는 되돌리기에 너무 커져 있었습니다.

다음에 비슷한 규모를 시작한다면, 화면 열 개쯤 만들어 본 시점에서 멈추고 공통 컴포넌트를 먼저 뽑을 것 같습니다. **그 시점이 가장 싸고, 그 이후로는 계속 비싸집니다.**
