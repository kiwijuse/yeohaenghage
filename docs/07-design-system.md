# 디자인 시스템

> 시안 한 벌로 화면 200개를 만들 때 생기는 일

[← 목록으로](../README.md#문서)

---

## 문제

디자이너는 한 가지 크기의 화면 위에서 작업합니다. 우리 시안은 **390 × 779** 였습니다. 여기서 779는 기기의 전체 세로 길이가 아니라, 상태바와 내비게이션 바를 뺀 **실제로 그릴 수 있는 영역**입니다.

시안은 한 벌인데 기기는 제각각입니다. 시안의 342px 카드를 어떻게 옮길 것인가 — 이걸 팀 규칙으로 먼저 정했어야 했습니다.

---

## 01 · 규칙을 세우려다 만 이야기

프로젝트 초반에 시안 기준을 현재 기기 비율로 환산하는 함수를 만들어 뒀습니다. 시안의 px를 그대로 적으면 알아서 비율을 맞춰 주는 방식입니다.

```dart
const double design_width  = 390;
const double design_height = 779;

double reWidth(double px)  => available_screen_width  * px / design_width;
double reHeight(double px) => available_screen_height * px / design_height;
```

의도는 분명했습니다. 디자이너가 "여백 16"이라고 하면 개발자가 `reHeight(16)`이라고 옮겨 적기만 하면 되니, 중간에 해석하거나 계산할 일이 없습니다.

**그런데 실제로는 거의 쓰이지 않았습니다.** 최종 코드에서 `reWidth`는 23곳, `reHeight`는 6곳에서만 호출됩니다. Dart 파일 110개 중 13개에서만 등장합니다.

대신 화면 대부분은 이렇게 쓰였습니다.

```dart
// 실제 코드에서 훨씬 자주 보이는 형태
width: MediaQuery.of(context).size.width * 0.9,
height: 180,
padding: const EdgeInsets.symmetric(horizontal: 20),
```

`MediaQuery`는 250곳에서, 고정 픽셀값은 2,100곳이 넘게 쓰였습니다.

### 왜 이렇게 됐나

규칙을 만들어 놓고 **강제하지 않았기 때문**입니다.

화면 하나를 급히 만들 때 `MediaQuery`로 바로 잡는 게 더 빠릅니다. 그렇게 만든 화면이 하나 생기면 다음 사람이 그걸 참고하고, 그 방식이 표준처럼 퍼집니다. 코드 리뷰에서 "이건 `reWidth`로 바꿔주세요"라고 짚는 절차가 없었으니 되돌릴 계기도 없었습니다.

**규칙은 만드는 순간이 아니라 지켜지기 시작하는 순간부터 규칙입니다.** 함수를 정의해 둔 것만으로는 아무것도 통일되지 않았습니다.

### 그래서 남은 결과

지금 코드베이스에는 크기를 정하는 방식이 **세 가지가 섞여** 있습니다. 환산 함수, `MediaQuery` 비율, 고정 픽셀. 어떤 화면이 어떤 방식으로 쓰였는지는 열어봐야 알 수 있습니다.

기기별로 크게 깨지지는 않았습니다. `MediaQuery` 비율도 나름대로 대응은 되니까요. 다만 **"이 앱은 크기를 이렇게 다룬다"고 한 문장으로 말할 수 없는 상태**가 됐고, 그게 디자인 시스템으로서는 실패한 지점입니다.

> [!NOTE]
> 다시 한다면 함수를 만드는 것보다 **첫 화면 몇 개에서 그 방식만 쓰이도록 만드는 것**에 시간을 쓰겠습니다. 초기 화면이 사실상 템플릿이 되기 때문입니다.

## 02 · 타이포그래피

두 서체를 함께 씁니다.

| 서체 | 쓰이는 곳 | 이유 |
|---|---|---|
| **Noto Serif KR** | 브랜드 문구 · 온보딩 · 주요 제목 | 명조체의 무게감이 "기억"이라는 브랜드 정서와 맞음 |
| **Pretendard** | 본문 · 버튼 · 목록 · 입력 | 화면용으로 설계된 서체라 작은 크기에서도 안정적 |

세리프를 제목에만 쓰는 건 흔한 조합이지만, 이 서비스에서는 특히 잘 맞았습니다. 여행하게의 카피는 `출발은 혼자, 기억은 같이` 처럼 짧고 감성적인 문장이 많습니다. 이런 문장은 명조체에서 훨씬 잘 읽힙니다. 반면 예약 화면의 숫자와 조건들은 고딕이 아니면 답답합니다.

---

## 03 · 아이콘

아이콘은 전부 SVG로 관리하고, 색은 쓰는 쪽에서 지정합니다.

```
images/icon/
├─ home_*        홈 · 하단 탭 (11개)
├─ travel_*      지도 · 검색 (8개)
├─ community_*   피드 · 글쓰기 (11개)
├─ message_*     채팅 (5개)
├─ profile_*     마이페이지 (11개)
├─ schedule_*    일정 (5개)
└─ manager_*     숙소 편의시설 (22개)
```

**파일 이름 앞에 화면 이름을 붙였습니다.** 폴더를 나누는 대신 접두어를 쓴 이유는, 파일 탐색기에서 정렬만 해도 화면별로 묶이고 검색할 때 `travel_`만 쳐도 관련 아이콘이 모두 나오기 때문입니다. 아이콘이 80개를 넘어가면서 이 규칙이 실제로 도움이 됐습니다.

`manager_` 접두어가 붙은 22개는 편의시설 아이콘입니다. 에어컨 · 세탁기 · 와이파이 · 주방 같은 것들인데, 숙소마다 어떤 시설이 있는지를 **비트마스크 하나**로 주고받습니다. 시설이 20개가 넘어도 정수 하나면 충분하고, 아이콘 목록을 그릴 때 비트를 순회하면 됩니다.

### 지도 마커는 미리 그려 뒀습니다

평점이 표시된 지도 마커는 런타임에 합성하지 않고 **미리 렌더링한 이미지를 씁니다.** 0.0부터 10.0까지, 선택 상태와 비선택 상태를 각각 준비했습니다.

지도에 마커 수십 개를 한 번에 그리는데, 마커마다 배경과 숫자를 합성하면 그 비용이 전부 지도가 움직이는 순간에 몰립니다. 미리 만들어 두면 이미지를 얹기만 하면 됩니다. 에셋 용량은 늘지만 앱 크기에서 차지하는 비중이 크지 않았고, **지도가 부드럽게 움직이는 쪽이 훨씬 중요했습니다.**

## 04 · 화면 가장자리까지 쓰기

앱은 상태바와 내비게이션 바 뒤까지 화면을 확장해서 그립니다. 시스템 바는 투명해집니다.

여기서 실무적인 문제가 하나 생깁니다. **상태바 아이콘 색이 배경에 따라 안 보입니다.** 흰 배경 화면에서는 아이콘이 어두워야 하고, 지도나 사진처럼 어두운 배경에서는 밝아야 합니다.

화면마다 자기 배경에 맞는 시스템 바 스타일을 선언하고, 화면이 전환될 때 그 값이 적용되도록 했습니다. 사소해 보이지만 이걸 빠뜨리면 **특정 화면에서만 상단 시계가 안 보이는** 현상이 생깁니다.

## 아쉬운 점

여기가 이 프로젝트에서 가장 크게 남은 빚입니다.

**공통 컴포넌트를 끝내 만들지 않았습니다.** 버튼 · 앱바 · 바텀시트 · 카드를 화면마다 다시 선언했습니다. 초반에는 화면을 빨리 찍어내는 데 유리했습니다. 남의 코드에 의존하지 않으니 서로 부딪히지도 않았고요.

문제는 화면이 100개를 넘어가면서 시작됐습니다. 버튼의 모서리 반경을 바꾸자는 얘기가 나오면 수십 곳을 고쳐야 했습니다. 실제로 호스트 이벤트 등록 화면 네 개는 서로 거의 같은 코드가 각각 1,300줄씩 들어 있습니다.

**150k줄이라는 숫자는 규모의 증거가 아니라 이 부채의 크기입니다.**

**색상도 같은 길을 갔습니다.** 브랜드 색을 상수로 모아 두지 않고 `Color(0xFF228B22)` 같은 값을 쓰는 자리마다 직접 적었습니다. 색을 하나 바꾸려면 전체 검색으로 찾아야 합니다. 크기에서 겪은 일을 색에서 똑같이 반복한 셈입니다.

**크기 기준이 하나 더 늘었습니다.** 초기 기준(390×779) 위에 온보딩을 만들면서 다른 기준(390×844)이 추가됐습니다. 어느 쪽이 맞는지 정리하지 않고 둘 다 남겨 뒀습니다.

## 마치며

이 문서를 쓰면서 알게 된 게 하나 있습니다. **디자인 시스템이라고 부를 만한 게 사실 없었습니다.**

시안 기준을 환산하는 함수를 만들었고, 아이콘 이름에 규칙을 뒀고, 서체를 용도별로 나눴습니다. 조각들은 있었습니다. 그런데 그것들이 **모든 화면에 실제로 적용됐는지**는 아무도 확인하지 않았고, 확인할 방법도 만들지 않았습니다.

그래서 규칙은 문서 안에서만 지켜졌습니다. 코드에서는 급한 대로 만든 방식이 표준이 됐습니다.

다음에 비슷한 규모를 시작한다면 순서를 바꾸겠습니다. 함수와 상수를 먼저 만드는 대신, **화면 열 개를 한 방식으로 끝까지 만들어 보고 거기서 공통점을 뽑아내겠습니다.** 그 열 개가 나머지 190개의 템플릿이 되기 때문입니다. 규칙을 먼저 선언하는 것보다 이쪽이 훨씬 잘 지켜집니다.
