# API 클라이언트

> 토큰 갱신이 동시에 여섯 번 나갔던 이야기

[← 목록으로](../README.md#문서)

---

## 문제

사용자가 며칠 만에 앱을 켭니다. 액세스 토큰은 이미 만료됐습니다.

홈 탭 하나가 뜨면서 요청 대여섯 개가 동시에 나갑니다. 커뮤니티 피드, 안 읽은 메시지 수, 다가오는 예약, 알림 개수, 프로필 정보. 이들이 **전부 401을 받습니다.**

각 요청은 "토큰이 만료됐으니 갱신하자"고 판단하고, **동시에 갱신을 시도합니다.**

여기서 터집니다. 서버는 리프레시 토큰을 1회용으로 회전시킵니다. 한 번 쓰면 폐기되고 새 토큰이 발급됩니다. 보안상 맞는 설계입니다. 그런데 클라이언트가 여섯 번 동시에 요청하면:

```
요청 A → 리프레시 성공 → 새 토큰 발급, 기존 토큰 폐기
요청 B → 이미 폐기된 토큰으로 리프레시 → 실패
요청 C → 이미 폐기된 토큰으로 리프레시 → 실패
...
```

**하나만 성공하고 나머지는 전부 실패합니다.** 실패를 "리프레시 토큰도 만료됨"으로 해석하면 강제 로그아웃까지 갑니다. 증상은 이렇게 나타났습니다.

> 며칠 만에 앱을 켜면 가끔 로그아웃돼 있다.

가끔이라는 게 최악이었습니다. 어떤 요청이 먼저 도착하느냐에 달린 경쟁 상태라 재현이 들쭉날쭉했습니다.

---

## 01 · 갱신을 함수가 아니라 Future로 다루기

해법의 핵심은 한 문장입니다.

> **갱신을 "호출할 함수"가 아니라 "여럿이 함께 기다릴 수 있는 하나의 작업"으로 만든다.**

먼저 도착한 요청이 갱신을 시작하고, 뒤늦게 401을 만난 요청들은 새 갱신을 시작하는 대신 **이미 진행 중인 작업을 함께 기다립니다.**

```dart
/// 현재 갱신이 진행 중인지
bool _is_refreshing = false;

/// 진행 중인 갱신 작업 그 자체
Future<bool>? _refresh_token_future;

Future<bool> handleTokenRefresh() async {
  // 누군가 이미 시작했다면 그 작업의 결과를 함께 기다린다
  if (_is_refreshing && _refresh_token_future != null) {
    return await _refresh_token_future!;
  }

  // 아무도 없다면 내가 락을 잡고 시작한다
  _is_refreshing = true;
  _refresh_token_future = refreshAccessToken().then((is_success) {
    _is_refreshing = false;
    _refresh_token_future = null;
    return is_success;
  });

  return await _refresh_token_future!;
}
```

여섯 개가 동시에 들어와도 **서버로 나가는 리프레시 요청은 정확히 한 번**입니다. 나머지 다섯은 같은 `Future`를 `await` 하다가 함께 깨어나고, 전부 같은 결과를 받습니다.

> [!NOTE]
> Dart는 단일 스레드 이벤트 루프 위에서 돕니다. `await` 사이에만 다른 작업으로 넘어가고, `if` 검사와 `_is_refreshing = true` 사이에는 끼어들 틈이 없습니다. 그래서 뮤텍스 없이 플래그만으로 충분합니다. 여러 스레드가 진짜로 동시에 도는 환경이었다면 이 코드는 안전하지 않습니다.

## 02 · 모든 요청을 한 통로로

이 락이 의미가 있으려면 **모든 요청이 같은 문을 지나야** 합니다. 하나라도 `http.get`을 직접 부르면 그 요청은 락 밖에서 갱신을 시도합니다.

그래서 `get`과 `post`를 감싼 얇은 래퍼를 두고, 앱 전체가 이것만 씁니다.

```dart
Future<http.Response> get(Uri url, {Map<String, String>? headers}) async {
  var response = await http.get(url, headers: await _getHeaders(headers));

  if (response.statusCode == 401) {
    if (await handleTokenRefresh()) {
      // 갱신에 성공했으면 새 토큰으로 한 번만 재시도
      response = await http.get(url, headers: await _getHeaders(headers));
    } else {
      onSessionExpired?.call();
    }
  }

  return _sanitizeHttpResponse(response);
}
```

재시도는 **한 번뿐**입니다. 갱신에 성공한 직후에도 401이 온다면 그건 토큰 문제가 아니라 권한 문제입니다. 반복해봐야 같은 결과입니다.

### 소켓도 같은 락을 씁니다

실시간 메시지용 Socket.IO 연결도 같은 토큰으로 인증합니다. 토큰이 만료되면 REST와 소켓이 **거의 동시에** 끊깁니다.

소켓 쪽이 자기만의 갱신 로직을 갖고 있으면 처음 문제가 그대로 재현됩니다. 그래서 소켓도 인증 실패 시 `handleTokenRefresh()`를 호출하고, 성공하면 새 토큰으로 핸드셰이크 정보를 갈아 끼운 뒤 재연결합니다.

```
REST 401 ─┐
          ├─▶ handleTokenRefresh()  ──▶ 서버 요청 1회
소켓 인증 실패 ─┘        (공유 락)
```

**REST와 소켓이 하나의 뮤텍스를 공유합니다.**

## 03 · 화면에 그리기 전에 한 번 거르기

두 번째 역할은 성격이 다릅니다.

커뮤니티 글, 닉네임, 채팅 메시지는 전부 사용자가 직접 쓴 값입니다. 여기에 **결합 문자를 잔뜩 쌓아 올린 입력**이 들어온 적이 있습니다. 글자 위아래로 기호가 흘러넘치는 형태(흔히 Zalgo 텍스트라고 부릅니다)인데, 텍스트 한 줄의 실제 높이가 폭발합니다.

증상은 이랬습니다. 커뮤니티 목록에서 **게시글 하나가 다른 게시글 영역까지 침범해** 레이아웃이 깨졌습니다.

서버에서도 막고 있었지만, 이미 저장된 데이터가 있었고 여러 경로로 들어오는 값도 있었습니다. **그리기 직전인 클라이언트에 방어선을 하나 더 두는 편**이 확실했습니다.

```dart
dynamic sanitizeResponseData(dynamic data) {
  if (data is String) {
    // 결합 문자가 3개 이상 연달아 붙은 구간을 제거
    // 한글 자모나 일반적인 발음 구별 기호는 이 길이를 넘지 않는다
    return data.replaceAll(RegExp(r'\p{M}{3,}', unicode: true), '');
  }
  if (data is List) {
    return data.map(sanitizeResponseData).toList();
  }
  if (data is Map<String, dynamic>) {
    return data.map((key, value) => MapEntry(key, sanitizeResponseData(value)));
  }
  return data;   // 숫자·불리언은 그대로
}
```

**응답 스키마를 특정하지 않고 재귀로 전체를 훑습니다.** 도메인마다 응답 모양이 다르고 중첩 깊이도 제각각이라, "이 필드만 검사"라고 정하면 새 API가 생길 때마다 빠뜨립니다.

### 함께 손봐야 했던 것

정제하고 나면 본문 길이가 줄어듭니다. `content-length` 헤더를 그대로 두면 실제 바이트 수와 어긋납니다.

```dart
final new_headers = Map<String, String>.from(response.headers)..remove('content-length');
```

그리고 JSON이 아닌 응답(HTML 에러 페이지, 평문)은 파싱에 실패하므로, 그때는 **원본을 그대로 흘려보냅니다.** 정제 로직이 실패해서 정상 응답까지 잃는 일이 없어야 합니다.

## 트레이드오프

| 선택 | 이유 | 감수한 것 |
|---|---|---|
| 재귀로 응답 전체 정제 | 새 API가 생겨도 자동 적용 | 응답이 클수록 순회 비용 · JSON을 한 번 더 인코딩 |
| 재시도 1회로 제한 | 무한 루프 방지 | 일시적 네트워크 오류는 사용자가 다시 시도해야 함 |
| 플래그 기반 락 | 단일 스레드 환경에서 충분 · 코드가 단순 | 진짜 멀티스레드였다면 안전하지 않음 |

**정제 비용은 실제로 무시할 수 없습니다.** 응답을 파싱하고, 전체를 순회하고, 다시 인코딩합니다. 지금 규모에서는 문제가 되지 않았지만, 목록 응답이 수백 건 단위로 커지면 문자열 필드만 골라 검사하는 쪽으로 바꿔야 합니다.

## 아쉬운 점

**갱신마저 실패했을 때의 처리가 비어 있었습니다.**

실제 출시 빌드에서 이 자리는 빈 함수였습니다. 리프레시 토큰까지 만료되면 아무 일도 일어나지 않았고, 사용자는 계속 401을 받는 앱을 보게 됩니다. 여기 실린 코드에서는 `onSessionExpired` 콜백으로 정리해 뒀지만, **원래 코드에는 그 연결이 없었다는 점을 그대로 적어 둡니다.**

이 문제가 오래 남아 있었던 이유는 단순합니다. **터졌을 때 알 방법이 없었기 때문입니다.** 크래시 리포팅이 붙어 있지 않았고, 로그는 릴리스 빌드에서 아무 데도 모이지 않았습니다. 갱신 실패는 앱이 죽지 않는 조용한 실패라 사용자 제보가 오기 전까지 존재 자체를 몰랐습니다.

**API 호스트가 31개 파일에 문자열로 흩어져 있었습니다.** 한 곳에 모아 두지 않아서 개발/운영 서버를 오가려면 전체 치환이 필요했습니다. 이건 처음부터 상수 하나로 뺄 수 있었던, 순수하게 게을렀던 부분입니다.

## 마치며

동시성 문제는 **평소에는 안 보이고 하필 중요한 순간에 보입니다.** 며칠 만에 앱을 켠 사용자, 즉 우리가 가장 붙잡아야 할 사용자가 정확히 이 조건을 만족합니다.

해결책 자체는 코드 열 줄입니다. 어려웠던 건 "가끔 로그아웃된다"는 제보에서 **여섯 개의 요청이 경쟁하고 있다**는 그림에 도달하는 과정이었습니다.
