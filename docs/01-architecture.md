## 01 · 무엇을 고를 수 있었나

개발자 2명, 디자이너 1명. 만들어야 하는 건 게스트 앱과 호스트 앱이 한 몸에 들어간 iOS · Android 앱.

이 조건에서 선택지는 셋이었습니다.

| 기준 | React Native | Flutter | 네이티브 2벌 |
|---|:---:|:---:|:---:|
| 하나의 코드로 두 플랫폼 | △ | ○ | ✕ |
| 스크롤 · 애니메이션 일관성 | △ | ○ | ○ |
| iOS와 Android가 같은 화면 | ✕ | ○ | ○ |
| 팀이 익히는 데 드는 시간 | ○ | ○ | ✕ |

네이티브 2벌은 사람이 부족해서 처음부터 불가능했습니다. 남은 건 React Native와 Flutter였습니다.

React Native를 깎아내릴 생각은 없습니다. 새 아키텍처의 JSI가 들어오면서 예전의 브리지 병목은 상당 부분 해소됐습니다. 다만 우리에게 결정적이었던 건 **세 번째 줄**이었습니다.

React Native는 결국 각 플랫폼의 네이티브 컴포넌트를 빌려 씁니다. 그래서 같은 코드가 iOS와 Android에서 미묘하게 다르게 보입니다. 디자이너가 한 명이고, 그 한 명이 시안을 한 벌만 그리는 상황에서 이건 실제 비용이었습니다. "안드로이드에서는 이 버튼이 좀 다르게 보여요"를 화면 200개에 대해 처리할 여유가 없었습니다.

Flutter는 OS에서 **빈 캔버스만 빌려온 뒤 자체 엔진으로 픽셀을 직접 그립니다.** 웹으로 치면 DOM을 쓰지 않고 Canvas에 전부 그리는 쪽에 가깝습니다. 플랫폼 컴포넌트를 빌리지 않으니 두 플랫폼이 픽셀 단위로 같습니다.

> [!NOTE]
> 이 선택에는 대가가 있습니다. 플랫폼이 기본으로 주는 접근성 동작을 공짜로 얻지 못합니다. 직접 챙겼어야 했는데 그러지 못했고, [아쉬운 점](../README.md#아쉬운-점)에 적어 뒀습니다.

## 02 · 화면이 그려지기까지

Flutter는 세 층으로 되어 있습니다. 문제를 디버깅할 때 **"지금 어느 층에서 터진 건가"**를 아는 것이 시간을 크게 줄여줬습니다.

```
┌─────────────────────────────────────────────┐
│  Framework  (Dart)                          │  우리가 쓰는 곳
│  Widgets · Rendering · Animation · Gestures │  위젯 · 레이아웃 · 제스처
├─────────────────────────────────────────────┤
│  Engine  (C/C++)                            │  픽셀이 실제로 만들어지는 곳
│  래스터라이저 · 텍스트 레이아웃 · Dart 런타임    │  프레임 스케줄링 · 합성
├─────────────────────────────────────────────┤
│  Embedder  (플랫폼별)                        │  OS와 맞닿는 곳
│  렌더 표면 확보 · 스레드 · 이벤트 루프          │  터치 · 키보드 · 플러그인
└─────────────────────────────────────────────┘
```

**Framework** 는 Dart로 쓰인, 우리가 매일 만지는 층입니다. 위젯 트리를 만들고 레이아웃을 계산합니다. 여기서 화면을 다시 그린다고 해서 네이티브를 왕복하지 않기 때문에, 스크롤과 애니메이션이 프레임을 안정적으로 유지합니다.

**Engine** 은 C/C++로 쓰인 실제 그리기 담당입니다. 여기서 겪은 대표적인 문제가 **첫 실행 때만 애니메이션이 끊기는** 현상이었습니다. 예전 렌더러는 셰이더를 처음 쓰는 순간에 컴파일했기 때문에, 그 화면을 처음 여는 사용자만 버벅임을 봤습니다. 개발자는 이미 여러 번 열어봤으니 재현이 안 되고요. 최신 렌더러가 셰이더를 빌드 시점에 미리 준비하면서 이 문제는 프레임워크 차원에서 해소됐습니다.

**Embedder** 는 OS마다 다른 층입니다. 그릴 표면을 OS에서 받아오고, 앱 스레드와 렌더 스레드를 세팅하고, 터치와 키보드 이벤트를 위로 전달합니다. [백그라운드 업로드 문제](06-background-upload.md)는 정확히 이 층에서 터졌습니다.

## 03 · 네이티브와 이야기하는 비용

Flutter가 직접 할 수 없는 일이 있습니다. GPS를 읽고, 카카오 지도를 띄우고, 결제 SDK를 부르는 일입니다. 이건 **Platform Channel**을 통해 네이티브에 요청합니다.

여행하게에서 이 통로를 가장 무겁게 쓰는 곳은 지도였습니다.

- 현재 위치를 기준으로 게스트하우스를 거리순 정렬
- 지도 위에 숙소 마커를 표시
- 지도 자체를 위젯 트리 중간에 끼워 넣기 (Platform View)

여기서 배운 것이 하나 있습니다. **통로를 지나는 데이터의 양보다, 통로를 지나는 횟수가 더 비쌉니다.**

마커 수십 개를 갱신할 때 마커 하나마다 채널을 호출하면, 그 직렬화/역직렬화 비용이 전부 UI 스레드에 쌓입니다. 지도를 드래그하는 동안 이 일이 계속 일어나면 프레임이 눈에 띄게 떨어집니다.

그래서 **마커 목록 전체를 한 번에 묶어서 넘기는** 쪽으로 바꿨습니다. 채널이 오가는 데이터는 JSON 문자열이 아니라 바이너리로 인코딩되기 때문에, 한 번에 큰 덩어리를 보내는 것이 여러 번 작게 보내는 것보다 훨씬 쌉니다.

> [!TIP]
> 마커가 수천 개 단위로 늘어난다면 채널 대신 FFI로 네이티브 메모리에 직접 접근하는 방법이 있습니다. 우리 규모에서는 배치 전송으로 충분했고, 필요하지 않은 최적화를 미리 하지 않았습니다.

이 문제를 근본적으로 줄인 건 채널 최적화가 아니라 **애초에 마커를 적게 그리는 것**이었습니다. → [지도 타일링](02-map-tiling.md)

## 04 · 앱의 뼈대

```
main()
 ├─ 스플래시 유지 (로그인 확인이 끝날 때까지)
 ├─ 서버 점검 확인 → 점검 중이면 여기서 멈춤
 ├─ 저장된 업로드 큐 복원 → 중단된 업로드 이어서 진행
 ├─ 푸시 · 알림 초기화
 └─ MultiProvider (상태 30개)
      └─ 로그인 여부 분기
           ├─ 온보딩 / 로그인
           └─ 홈 셸
                ├─ IndexedStack (탭 5개를 모두 살려 둠)
                ├─ 하단 탭바 (권한에 따라 게스트/호스트 전환)
                └─ SocketManager (실시간 메시지)
```

몇 가지 의도적인 선택이 있습니다.

**탭을 `IndexedStack`으로 쌓아 둡니다.** 탭을 옮길 때마다 화면을 새로 만들면 스크롤 위치와 입력 중이던 내용이 날아갑니다. 다섯 화면을 모두 살려 두는 대신 메모리를 조금 더 씁니다. 커뮤니티 피드를 한참 내리다가 메시지를 확인하고 돌아왔을 때 그 자리에 그대로 있는 것이, 이 앱에서는 메모리보다 중요했습니다.

**점검 확인을 첫 프레임 전에 합니다.** 서버가 내려가 있는데 앱이 정상적으로 열리면 사용자는 화면마다 다른 에러를 봅니다. 그럴 바에는 처음에 한 번 명확히 알리는 편이 낫습니다. 다만 네트워크 자체가 끊긴 경우는 점검으로 취급하지 않습니다. 지하철에서 앱을 켰다고 "서버 점검 중"이라고 하면 안 되니까요.

**권한이 바뀌면 탭 전체가 교체됩니다.** 호스트 모드로 전환하면 하단 탭 다섯 개가 통째로 바뀝니다. 게스트 화면과 호스트 화면을 한 탭 안에서 분기시키지 않고 셸 수준에서 갈랐습니다. 두 모드는 사실상 다른 앱이고, 화면 안에서 `if (isHost)`로 나누기 시작하면 그 조건문이 모든 화면으로 번집니다.

## 마치며

프레임워크를 고르는 일은 기능표를 비교하는 일이 아니라, **우리 팀이 감당할 수 있는 실패 유형을 고르는 일**에 가까웠습니다.

Flutter를 고르면서 우리는 "플랫폼별로 화면이 미묘하게 다른 문제"를 피하는 대신 "플랫폼이 공짜로 주던 것을 직접 챙겨야 하는 문제"를 떠안았습니다. 사람이 셋인 팀에서는 전자가 훨씬 비싼 문제였고, 그래서 후회하지 않는 선택입니다. 다만 후자를 충분히 갚지 못한 건 사실이고, 그건 프레임워크가 아니라 우리 몫이었습니다.
